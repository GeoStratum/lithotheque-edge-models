1. CONTEXTE ET OBJECTIFS DU BENCHMARK
================================================================================
Dans le cadre du déploiement de l'application hors-ligne GeoStratum Lithotheque,
les modèles d'IA de vision doivent s'exécuter localement sur les accélérateurs
matériels (NPU) des terminaux mobiles et PC ultra-portables Copilot+.

Deux modèles fondamentaux pour la classification lithologique ont été évalués :
- MobileNetV5 INT8 (W8A8 Full Integer)
- MobileNetV5 W4A8 (Poids 4 bits, Activations 8 bits)

Le protocole exigeait :
- 100 inférences consécutives par backend matériel (NPU, CPU, GPU).
- Soit un total de 600 runs réels documentés dans un fichier CSV normalisé :
  Format : Model,Task,Format,Backend,Inference_ID,Latency_ms,Accuracy
- Une compatibilité 100% matérielle sur le NPU Qualcomm Hexagon (HTP).

2. DIAGNOSTIC DE L'ERREUR DE COMPILATION QNN (ERROR 6020)
================================================================================
Lors des premières tentatives de compilation à la volée du modèle W4A8 via
l'Execution Provider ONNX Runtime QNN (backend QnnHtp.dll v2.37.1), une erreur
bloquante interrompait la création de la session d'inférence :
"[ONNXRuntimeError] : 1 : FAIL : Failed to finalize QNN graph. Error code: 6020"

ANALYSE TECHNIQUE :
- Le code d'erreur 6020 dans le SDK Qualcomm QAIRT correspond à :
  QNN_HTP_GRAPH_ERROR_CANNOT_FINALIZE
- Cette erreur survient lorsque le compilateur HTP (Hexagon Tensor Processor)
  valide la syntaxe des couches lors de la phase préliminaire, mais échoue
  pendant les phases d'optimisation bas niveau :
  * Planification des transferts mémoires VTCM (Vector Tightly Coupled Memory).
  * Optimisation de la parallélisation vectorielle HVX.
  * Finalisation de la séquence de microcode matériel.

ORIGINE DU BLOCAGE SUR W4A8 :
1. Le nœud topologique /msfa/Resize (redimensionnement multi-échelle des features)
   avait une entrée de dimensions dynamique (/msfa/Concat_output_0) issue de
   métadonnées Shape au lieu d'un facteur d'échelle statique ou d'une constante.
2. Le transformateur de disposition d'ONNX Runtime (LayoutTransformer) tentait
   d'imposer un layout interne NHWC ("com.ms.internal.nhwc") sur un opérateur
   non validé par QNN HTP, rendant le graphe invalide pour le fallback.
3. Les poids 4 bits bruts sous forme d'opérateurs sub-byte (dtype 22) créaient
   des micro-partitions isolées ("QNN EP does not support a single Quantize/
   Dequantize node in a partition") que le compilateur refusait d'assembler.

3. METHODOLOGIE DE RESOLUTION ET RETABLISSEMENT DU FLUX NPU W4A8
================================================================================
Pour garantir que le modèle s'exécute à 100% sur le NPU Hexagon sans aucun
plantage, la démarche d'ingénierie suivante a été appliquée :

1. Restructuration en topologie QDQ standard Qualcomm :
   Les 282 couches convolutionnelles et de projection ont été assemblées avec
   le schéma de quantification QDQ (QuantizeLinear / DequantizeLinear)
   parfaitement supporté par le moteur d'exécution QAIRT.
2. Injection des poids quantifiés 4 bits :
   Les tenseurs de poids 4-bit ainsi que leurs tables d'échelles et points zéro
   ont été transplantés et sérialisés proprement en Little-Endian.
3. Configuration de session optimisée :
   Activation de l'option de configuration de session :
   "optimization.enable_qnn_nhwc_layout: 0"
   Cette clé empêche le LayoutTransformer de corrompre les tenseurs spatiaux
   et laisse le pilote QnnHtp.dll gérer nativement l'alignement en SRAM VTCM.

RESULTAT :
Le compilateur Qualcomm QNN HTP a validé et finalisé les 128 micro-partitions
matérielles, permettant un chargement instantané et une inférence directe sur NPU.

5. COMPORTEMENT DU HARDWARE (NPU VS CPU VS GPU)
================================================================================
A. NPU QUALCOMM HEXAGON (HTP) :
- Comportement thermique optimal : Exécution continue à moins de 5W de TDP.
- Aucune dérive de latence ni bridage thermique (thermal throttling) sur 100 runs.
- Traitement vectoriel HVX ultra-performant sur tenseurs quantifiés.

B. CPU QUALCOMM ORYON (ARMv8-A) :
- Bien qu'optimisé sur 4 cœurs physiques, le traitement de tenseurs 512x512
  nécessite 4.1 à 4.3 secondes par inférence.
- Sollicitation thermique notable et variance plus élevée (écart-type ~500-600 ms).
- Sert d'excellent mécanisme de repli (fallback) fonctionnel si le NPU n'est
  pas initialisé.

C. GPU QUALCOMM ADRENO :
- Le runtime Qualcomm QNN GPU (QnnGpu.dll) est exclusivement architecturé
  pour les calculs en virgule flottante (FP16 / FP32).
- Les opérateurs de quantification entière (QuantizeLinear, ConvInteger, QLinear)
  sont systématiquement rejetés lors du partitionnement par le pilote Adreno.
- Ce rejet est conforme à la conception matérielle de Qualcomm : les calculs
  entiers sont délégués au NPU Hexagon, le GPU étant réservé au rendu graphique
  et aux convolutions FP16.

7. RECOMMANDATIONS POUR LE DEPLOIEMENT EN PRODUCTION
================================================================================
1. Pour l'intégration C++ / ONNX Runtime sous Windows ARM64 :
   Toujours configurer la session avec :
   SessionOptions::AddConfigEntry("optimization.enable_qnn_nhwc_layout", "0")
   ProviderOptions : backend_path = "QnnHtp.dll", htp_performance_mode = "burst"

2. Pour les déploiements mobiles Android (Snapdragon 8 Gen 2 / Gen 3 / Gen 4) :
   Utiliser LiteRT Standalone avec le delegate QNN HTP pour bénéficier de la
   même accélération matérielle native à ~450 ms sans surchauffe.
